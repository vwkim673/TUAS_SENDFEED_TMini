## G. Post-live-test fixes (2026-07-19) — first live batch examined (`20260716_LiveTest`)

First live PLC batch (FRONT+REAR, 10 jobs each, `FORCE_ROI_MODE=1`) surfaced two bugs; both
fixed in `SampleVisionaryTMini.cpp` (no header/vcxproj change) and **re-run validated**.

1. **VA chassis-type count TIE → blanked VA (IGH).** `chassis_type_selection_va` decided type
   by class COUNT with strict `>`. A normal IGH shows 1 guide + 1 cone → `xt_counter`(cone)==
   `igh_counter` → fell to `"unknown"` → no target → `XT_index=-1` (looked like "no VA"). Hit
   4 REAR jobs (Center/Small IGH CHS45: 161509/162728/163055/163208), VA 0–2%. **Fix:** (a)
   guide-types OVERRIDE the cone count (`igh_counter>0 ⇒ IGH`; an XT never contains a guide,
   an IGH legitimately shows a cone); (b) the PLC job type (`jobInfo.chassisType`) is now
   AUTHORITATIVE for target selection — the VA count is a logged cross-check only (mismatch →
   `[VA] chassis-type mismatch … (using PLC)`), applied BEFORE the VA pipeline (the old PLC
   fallback ran too late, after target/deviation/landout/clps). **Re-run: all 20 jobs VA 100%,
   `XT_index=-1` count = 0.**
2. **IGH ROI crop X-window not job-position aware → empty crop → no 3D.** `fillRoiParams` IGH
   branch overrode `roiPrm.xMin/xMax` with the `IGH_ROI_40/45` box, keyed by sensor+CHS length
   ONLY. REAR IGH CHS40 Big (~+900) and Center/Small (~−730) sit on OPPOSITE trolley sides, so
   the single box window `+350..+1300` left Center/Small OUTSIDE → empty crop. Also on FRONT
   the box put CHS45 Center/Small at `+500..+1150` (FALSE 3D on deck at ~+785) when the true
   guide is at ~−800. **Fix:** IGH keeps `presetRangeX` for the trolley X-window (job-position
   aware, like XT), takes only Y/Z/coneY/xspan from the box. `presetRangeX` values validated
   against the live guide positions for every FRONT+REAR config.
   **Re-run:** REAR Center CHS40 0→48% 3D, REAR Small CHS40 0→53%, FRONT CHS45 Center/Small
   moved to the correct −800 side.

3. **Region extraction starved on guide-only IGH (REAR CHS45).** After fix #2 the crop found
   the guide (~2600 pts, +773 side) but `chassis_roi_extract_region` still returned empty on the
   CHS45 Center/Small clips (162728/163055/163208 → 3D 0%; 161509 only 19%). Cause: `candBand`
   = `coneY ± 140`, but the preset REAR CHS45 `coneY=−66` sits ~300mm ABOVE the actual guide mass
   (~−375). A **guide-only** IGH (`ighs`) has no twist-lock cone poking up near −66, so the band
   caught only the sparse tail → no 40mm column reached `minColPts=60` → `coneColumns` empty. (The
   CHS40 jobs survived because their `igh` cone tip pokes into the band.) **Fix (`ChassisRoi.h`):
   fallback re-centre — if the preset-`coneY` band yields no column, re-centre `candBand` ONCE on
   the crop's near-Z structure height (`coneHeightEstimate`) and retry; preset stays authoritative
   where it already forms columns (CHS20 wheel case never triggers it). Replay: 163055 0→27/27,
   163208 0→91/91, 162728 0→51/51, 161509 81→417/420 frames extract.**

**Rebuild + re-run (2026-07-20) — all three fixes confirmed end-to-end:**
- VA 100% on all 20 jobs (0 `XT_index=-1`).
- REAR CHS45 Center/Small 3D: 0/0/0/19% → **100/100/100/99%** (extraction fallback works live).
- REAR CHS40 Center/Small 3D: 0/0 → 48/53%. FRONT Small CHS40 51→96%. FRONT CHS45 on correct side.

4. **IGH extraction targeted the WRONG STRUCTURE (cone/post, not the guide) — fixed (`ChassisRoi.h`).**
   Investigating the Big IGH "jitter" / large `|dH|` revealed the real bug: an IGH shows a twist-lock
   cone/post ~250mm ABOVE the guide and NEARER-Z. `candBand = coneY±140` (preset coneY −4/−7 FRONT,

   not `coneY`. IGH-gated (`prm.guideDenseY`, set in `fillRoiParams`) → XT untouched; supersedes the
   #3 empty-fallback for IGH (guide-centred band never starves). Offline replay (20260716 batch): target
   moves from ~+60 (cone/post) to the guide top ~−150..−190 on ALL FRONT+REAR IGH jobs, and is MORE

## C. XT Center 2-cone (40ft chassis, 20ft job, center sensor)

The center crop contains BOTH twist-lock cones; VA (when valid) already picks the single target
cone, so it uses the **normal** path. The ROI 2-cone end-selection is a **fallback**:

- **VA valid → existing logic**: `target_on_right` normal (Big → right/max-X, Small → left/min-X),
  normal single-cone deviation. **Unchanged.**
- **VA catches < 2 cones (or fails) → ROI end-selection**: with only one cone you can't tell the
  front from the rear, so drop to ROI. Gate: `vaInRange` also requires `cone(idx1)+land(idx2) >= 2`
  for the 2-cone case.
- Helper **`xt_center_end_target(region, targetMaxX, inset)`**: wide near-Z band (3rd-pct Z +150 +
  upper-half) over the FULL `roiCrop` (both cones) → outer X extreme (max/min by job) →
  `tx = extreme ∓ inset`; Z = near-Z; **Y = `chassis_roi_corner_height` (plate corner, not cone top)**.
- **3D deviation**:
  - offsets corrected to **X = 26, Z = 14** (were on the wrong axes). Non-2-cone:
    `dev_x = cone − (tor? hole+26 : hole−26)`, `dev_z = cone − (hole+14)`.
  - **2-cone (ROI cone only, `coneFromRoiEnd`)**: `dev_x = (cone ±26) − (hole ±167)` (Big +, Small −);
    the corner-casting width (167) aligns the hole to the ROI cone's END corner. A **valid VA cone
    uses the normal deviation** — the 167 form is gated to `centerTwoCone && (FORCE_ROI || _coneSrc==3)`.
  - **RS (rear) sensor mirrors the deviation X and Z** (deviation phase only; positions as-is).
- INI: `CORNER_CASTING_W=167`, `XT_TWOCONE_INSET=130`.

**Validation:** lateral (X) direction fixed — FRONT Small dX≈3mm (matches GT), REAR Big clean job
862 dX −19 / dY +5 / dZ +3. **REAR Big 696/435 remain off** (the deeper/sparse max-X cone is

## D. Sensor connection / reconnection (restored)

Previously the reconnect trigger was dead (`if (enable_process && false)`) and a silent stream
drop left `connected=true` forever. Now:

- **Auto-reconnect enabled** — control thread reconnects on failure; on runtime drop the stream
  thread wakes it immediately.
- **Stream-stall = disconnect** — no new frame for `STREAM_FRAME_TIMEOUT` (2000 ms) while streaming
  → `connected=0, fault=1` → reconnect.
- **Retry-count limit** — `MAX_RECONNECT_ATTEMPTS` (10) consecutive failed setups → give up, **fault
  latched**. A re-enable or a fresh drop resets the counter. Command-driven backup restarts a fresh
  cycle after a 10 s cooldown (without clearing fault).
- **Accurate `connected`/`fault` bits to the PLC (byte2 bit2/3):**

  | state | connected | fault |
  |---|---|---|
  | connected & streaming | 1 | 0 |
  | setup failing (retrying) | 0 | 1 |
  | gave up after N | 0 | 1 (latched) |
  | runtime drop | 0 | 1 → auto-reconnect |
  | clean disable | 0 | 0 |

- INI: `MAX_RECONNECT_ATTEMPTS=10`, `STREAM_FRAME_TIMEOUT=2000`.
